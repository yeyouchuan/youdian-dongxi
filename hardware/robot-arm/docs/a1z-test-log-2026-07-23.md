## Hardware and software

- Host: Apple Silicon macOS 26.5.2.
- Adapter: HHS `CANFD Analyser`, USB `a8fa:8598`, serial
  `F080205237584E31`.
- CAN: classical CAN at 1 Mbps through PyUSB/gs_usb.
- SDK: `userguide-galaxea/GALAXEA-A1Z`, `gripper` branch, commit
  `e931ecd0e25ad35df251097ba42921b3d2fa7224`.
- DimOS: commit `10793320a6693b00f82d6f26c7ce77043fa7c6a8`.

The public Galaxea SDK supports Linux SocketCAN directly. The macOS tests use
the local compatibility layer in `scripts/a1z_hhs_transport.py`.

## Transport findings

1. HHS is not a `/dev/cu.*` serial device. PyUSB finds it by VID/PID.
2. Control descriptors work and report firmware 2, hardware 1, 80 MHz CAN
   clock.
3. The generic `gs-usb` package does not include HHS in its device allowlist.
4. HHS bulk OUT is endpoint `0x01`; generic `gs-usb` hard-codes `0x02`.
5. Bulk IN `0x81` carries CAN frames.
6. HHS returns transmitted frames as `python-can` messages with
   `is_rx=False`; actual motor feedback has `is_rx=True`.
7. Echoes must be drained before returning from a non-blocking receive, with a
   hard maximum of 16 echoes per call. Otherwise the 100 Hz control loop can
   either starve real feedback or spend unbounded time draining echoes.

## Mandatory gates before another six-axis motion

Do not call the vendor `ArmRobot.start()` with nonzero position gain until:

1. TX echoes are filtered by the verified transport wrapper.
2. All six motors have delivered real feedback.
3. The measured positions are converted into URDF coordinates and checked
   against all soft limits.
4. Startup uses zero position gain.
5. The zero-gain running state matches the primed pose.
6. Only then is position hold enabled at the measured pose.

Trajectory validation must require actual measured displacement, not merely an
absolute error threshold larger than the commanded test step.

The corrected startup and feedback gates in
`scripts/a1z_six_axis_test.py` are verified on hardware. Large coordinated
motion is not verified. The runner now supports a no-trajectory preflight and
selected-joint diagnostics:

## Mandatory operating rules

These rules apply to every future run:

1. **Power-on:** connect the 24 V supply, wait several seconds for drive-board
   initialization, then start the control program.
2. **Power-off:** first move to a stable, center-of-mass-near-base safe pose;
   wait until motion stops; only then disable and remove power.
3. **No brakes:** loss of power or motor disable makes the arm fall. Support
   it before shutdown and keep an operator at the PSU switch.
4. **Gravity compensation:** the first validated run must use a factor no
   greater than 0.3. Confirm compensation lifts/supports rather than accelerates
   the arm downward before increasing toward 1.0.
5. **Joint limits:** validate and clamp every joint-space or IK result against
   the six soft limits before interpolation.
6. **Long moves:** interpolate at a bounded speed; never send a far target in
   one step.
7. **SIGINT/SIGTERM:** the motion runner must catch both, request the SDK soft
   estop from a separate watcher thread, abort the current interpolation, then
   call `robot.stop()`. Do not start another trajectory after an interrupt.
   An operator must support the arm because final disable removes all holding
   torque.
8. **Daily checks:** verify CAN communication, temperature, smooth manual
   motion, and absence of binding or unusual noise before enabling.

## Mandatory shutdown sequence

`robot.stop()` disables motor torque; on this no-brake arm that can cause the
same immediate drop as cutting 24 V power. A normal test must shut down in
this order:

1. Keep 24 V power on and keep the control loop running.
2. A runtime trajectory may first return to its run baseline, but that is not
   a shutdown pose.
3. In the main thread, interpolate all six joints to
   `[0, 0, 0, 0, 0, 0]` using exactly 60 commands at 60 Hz with
   `10t³ - 15t⁴ + 6t⁵` minimum jerk.
4. Confirm all six measured joints are within 5° of zero while the motors
   remain enabled.
5. Block at an operator interlock until the operator physically supports the
   arm.
6. Call `robot.stop()` to disable motor torque.
7. Only after the arm is supported and stable may the operator switch off the
   24 V supply.

The runner attempts this baseline return on both success and recoverable
software failures. It must not start a new return trajectory after SIGINT,
SIGTERM, stale feedback, a stopped control loop, an out-of-limit pose, or
another hard safety fault; in those cases the operator must support the arm
immediately while the process disables it.

### Return defect and recovery

The first version of `a1z_coordinated_demo_test.py` incorrectly stored the
commanded `WAKE_LOOK` target as a verified return waypoint even though the
measured pose had not converged to it. Its return verification failed, but the
`finally` block still printed a misleading safe-baseline message and disabled
at the elevated pose. This violated the required normal shutdown sequence and
caused the no-brake arm to sag.

The operator was instructed to support the arm and keep 24 V power on. A
return-only recovery run then:

1. primed the sagged measured pose
   `[-2.81, 0.36, -5.58, 31.31, -0.99, -66.50]°`;
2. rebased the command on measured feedback;
3. returned at `0.04 rad/s`;
4. reached `[-9.52, 0.36, -6.35, 38.65, -0.86, -80.47]°`;
5. confirmed every joint within 5° of the recorded run baseline;
6. held for two seconds before disabling.

Final MOS temperatures were `25.0–33.0°C`. No gripper or contact action was
commanded.

This recovery was still not a valid shutdown: the recorded run baseline was
not the official all-zero pose. When the motors were disabled, the arm fell.
The operator reported this after the run. Returning to a run baseline must
never again be described as safe for disable.

### Corrective changes

The coordinated runner now:

- replans from measured feedback instead of stale commanded targets;
- limits adaptive recovery subsegments to 20°;
- requires physical convergence before advancing;
- supports an explicit return-only baseline;
- prints “safe baseline confirmed” only after measured convergence;
- reports an unconfirmed return as an error instead of silently treating it
  as safe.

After the reported fall, all hardware runners were additionally changed to:

- use one shared, main-thread, 60-frame/60 Hz quintic zero-homing function;
- verify measured convergence to the official all-zero pose;
- keep the robot active after homing;
- block on the exact operator acknowledgement `PARKED_SUPPORTED`;
- call `robot.stop()` only after that physical-support acknowledgement;
- treat SIGINT/SIGTERM as a request for synchronous zero homing while the
  control loop remains healthy, rather than immediately latching estop.

If the control loop has already stopped or feedback is unsafe, software cannot
home the arm. The operator must support it immediately; power loss cannot be
recovered by software.

Do not run `WAKE_LOOK` or the high `AIR_PICK_PRE` stage again yet. After the
reported shutdown fall, the next hardware round must contain no Demo motion:

```text
current pose -> all-zero -> enabled hold -> parking confirmation
             -> operator support -> motor disable
```

Only after that standalone shutdown chain passes may a new powered session
execute `baseline -> WAKE_LOOK -> baseline`, followed again by all-zero
homing and the parking/support interlock.
